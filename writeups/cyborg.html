Cyborg — Write-up

A step-by-step investigation of the TryHackMe Cyborg room, from exposed Squid proxy credentials and a password-protected BorgBackup repository to an SSH foothold and privilege escalation through an unsafe backup script.

TryHackMeEasyNmap · GobusterJohn the RipperBorgBackupLinux PrivEsc

Scope: This walkthrough documents a controlled TryHackMe training environment. The target IP belongs to the lab session and may change. Both flags are hidden behind click-to-reveal controls.

01 / Reconnaissance

Port and service discovery

I started by identifying services exposed on the target using an Nmap version scan.

nmap -sV -T4 10.49.182.166

The scan showed two key services: SSH (22/tcp) and HTTP (80/tcp). HTTP was served by Apache, so web enumeration was the next logical step.

Directory enumeration

I used Gobuster with a common directory wordlist to discover endpoints that were not directly linked from the homepage.

gobuster dir -u http://10.49.182.166 -w /usr/share/dirb/wordlists/common.txt

The results pointed to /admin/ and /etc/. Both warranted closer inspection: the first contained application content, while the second exposed a directory of configuration files.

02 / Squid credentials

Under /etc/squid/, I found squid.conf and passwd. The configuration used HTTP Basic Authentication with the basic_ncsa_auth helper and a password database located at /etc/squid/passwd.

auth_param basic program /usr/lib64/squid/basic_ncsa_auth /etc/squid/passwd
auth_param basic children 5
auth_param basic realm Squid Basic Authentication
auth_param basic credentialsttl 2 hours
acl auth_users proxy_auth REQUIRED
http_access allow auth_users

The important access-control rule is http_access allow auth_users: the proxy permits requests when the authentication ACL matches. The passwd file contained an account called music_archive and an Apache MD5 ($apr1$) password hash.

Password recovery

Because the hash was accessible in the lab, I saved it to a local file and tested it with John the Ripper and the rockyou.txt wordlist.

echo '$apr1$BpZ.Q.1m$F0qqPwHSOG50URuOVQTTn.' > hash.txt
john --wordlist=/usr/share/wordlists/rockyou.txt hash.txt

John recovered the password squidward. This did not automatically grant SSH access: its relevance became clear when I investigated the backup archive referenced by the web content.

03 / BorgBackup investigation

The administration page exposed an archive download. I downloaded the .tar file and extracted it locally. The extracted content was a BorgBackup repository, not an ordinary collection of MP3 files.

On my local Kali environment, I could use explorer.exe . to open the current directory in Windows Explorer, then navigate to the extracted repository. This step was just local file management and was not part of the exploit.

Listing the archive

In Borg, a repository stores one or more backups called archives. The :: syntax identifies a particular archive inside the repository.

borg list .
borg list .::music_archive

The first command lists the available archives; the second lists files stored inside music_archive. The repository contained a user home-directory backup, including note.txt and secret.txt.

Reading the note

Using Borg's --stdout option, I viewed the note without extracting it to a local file.

borg extract --stdout .::music_archive home/alex/Documents/note.txt

The note provided credentials associated with the user alex. I used those findings for the next phase instead of assuming that the recovered Borg password was also the SSH password.

04 / Initial access

With the credentials discovered in the backup, I connected to the exposed SSH service as alex.

ssh alex@10.49.182.166

The login provided an authenticated shell and allowed me to retrieve the first flag.

05 / Privilege escalation

Checking sudo permissions

After establishing a shell as alex, I checked what commands the account could execute with elevated privileges.

sudo -l

The sudo policy permitted the backup script /etc/mp3backups/backup.sh to run as root without a password (NOPASSWD). This made the script an important attack surface.

Reviewing the script

The script included an argument parser that accepted a value after -c and stored it in a variable named command.

while getopts c: flag
do
    case "${flag}" in
        c) command=${OPTARG};;
    esac
done

getopts c: flag means that -c requires an argument. OPTARG contains the supplied value. This assignment is not a vulnerability by itself; the dangerous condition arises if a privileged script later executes or otherwise trusts that user-controlled value.

Observed privileged execution

In this lab, passing a command through the script's -c option led to a root shell:

sudo /etc/mp3backups/backup.sh -c "sudo su"

The script also produced tar warnings because the hard-coded MP3 paths did not exist. Those errors did not establish that the privilege-escalation step failed.

Why this matters: A passwordless sudo rule becomes risky when the authorized script can execute user-controlled commands. The screenshot shows only part of the script, so the exact later execution statement cannot be established from this excerpt alone.

06 / Restoring terminal output

After entering the root shell, commands such as whoami, id and ls appeared to run without printing results. However, error output was still visible.

This suggested that stdout (file descriptor 1) was no longer pointing to a visible destination, while stderr (file descriptor 2) was still usable. I redirected stdout to the same destination as stderr:

exec 1>&2

Using exec without another command applies the redirection to the current shell. Afterwards, normal output appeared again, allowing me to verify the shell and inspect root-owned files.

I then read the final flag from the root user's home directory.

cat /root/root.txt
⚑Root FlagClick to reveal ⌄
flag{Than5s_f0r_play1ng_H0p£_y0u_enJ053d}

Spoiler: this is the flag recovered during the lab.

07 / Lessons learned

  • Web enumeration: Exposed administrative and configuration directories can reveal useful entry points.
  • Credential hygiene: Password hashes and archived notes can expose credentials; avoid password reuse and publishing sensitive backup contents.
  • Backup forensics: Borg repositories contain archived file trees; borg list inspects contents and borg extract --stdout reads selected files.
  • Sudo hardening: Avoid passwordless execution of scripts that interpret user-controlled command parameters.
  • Linux I/O: A shell may still execute commands when stdout is broken or redirected. FD 1 and FD 2 can have different destinations.
